## 計画JSON

`inventory.json` に、比較が必要な条件と出力を根拠から先に列挙する。[境界ごとのケース設計](case-design.md)に沿って `conditions.json` を展開してから、テスト項目を `plan.json` に記録する。表は `check_coverage.py plan plan.json --conditions conditions.json --inventory inventory.json` の出力を使う。値は、下記のオブジェクト・配列・列挙値を示した箇所を除き、空欄のない文字列とする。IDは各配列内で一意にし、既知の調査漏れを分母から取り除かない。

[架空CLIの必須項目](../assets/inventory-example.json)・[条件例](../assets/conditions-example.json)・[計画例](../assets/plan-example.json)は、入口1件の記入例として使える。実案件では架空の根拠と期待値を調査結果に置き換える。

| キー | 形と記録する内容 |
| --- | --- |
| `scope` | オブジェクト。 `current` と `candidate` は実行記録の `revision` と一致する現新の識別子。 `inventory` に照合手順、実効設定、対象外とその根拠を記す。 |
| `targets` | 入口の配列。 `id`, `entry`, `evidence`, `oracle`, `execution`, `fixtures`, `isolation`, `checks`, `layers`。 `oracle` は `live`、来歴つきの実測記録である `captured`、比較元なしの `unavailable`。 `execution` は等価な初期状態と隔離した実行経路を用意できる `ready` または `blocked`。 `fixtures` はリセット方法、同一性の確認手順、固定要素。 `isolation` は確認した設定・実行境界、または不足している条件。 |
| `observations` | 観測項目の配列。 `id`, `target`（入口ID）, `layer`, `field`（条件の `outputs` と同じ個別項目名）, `evidence`, `method`（現新それぞれの採取方法・観測時点）, `mode`。 `effects` では `containment`（宛先と副作用の遮断・確認方法）も必須。 `mode` ごとの必須項目は下表のとおり。 |
| `risks` | 比較項目の配列。 `id`, `observation`（観測ID）, `dimension`（観点キー）, `priority`（`high` または `normal`）, `condition`（入力・前提・差分を起こす条件）, `expected`（観測すべき具体的な振る舞い）, `evidence`。 `design` は `model`、展開した `values`、検出する `regression` を持つ。ケースを計画できない項目には `gap: {"reason": "...", "next": "..."}`。 |
| `cases` | シナリオの配列。 `id`、`scenario`（前提、操作順、採取タイミング）、`steps`（採取点を実施順で並べた配列）。採取点には、一意の `id` と、比較項目と同じ `target`・`values`、`covers`（その操作で判定するリスクID）を記す。同じリスクを同じケースの複数の採取点に重ねて登録する場合は、採取時点ごとにリスクを分ける。 |

### 入口別の3層と観点

`targets[].layers` は `direct`（直接出力）、`state`（永続化データ）、`effects`（外部副作用）の3キーを持つ。値はそれぞれ `{"status": "...", "evidence": "..."}`。該当層は `required` とし、比較する観測を登録する。作用がないことを根拠で確認できる場合は `na` とする。存在や適用を確定できない場合は `open` とし、調べた箇所と残る調査を書く。対象内の入口には少なくとも1層を `required` または `open` として残す。作用は確認できていて観測手段がない場合、`required` のまま比較項目に `gap` を付ける。

`targets[].checks` は下表の全キーを持ち、各値に `status` と `evidence` を記す。失敗条件を特定した観点は `risk` とし、該当リスク行を作る。 `na` には除外根拠、 `open` には不足する根拠と次の調査を書く。複数の観点に当たる場合、互いに異なる失敗条件を行として残し、同じ主張には共通の根拠を参照する。

| キー | 両側のどこを調べるか |
| --- | --- |
| `legacy` | 旧テスト、仕様と実測の不一致、古いデータ、暗黙の既定値、互換利用を示す呼び出し側。 |
| `input` | NULL・欠損・空・ゼロの区別、型変換、入力上限、未知フィールド、検証順、既定値。 |
| `numeric` | 整数幅、符号、精度、半端値、丸め、単位、桁溢れ、比較演算。 |
| `time` | TZ、夏時間、UTC換算、日付境界、精度、期限、時計とタイマー。 |
| `text` | エンコード、Unicode正規形、改行、空白、ケース変換、ロケール。 |
| `order` | 順序契約、ソートキー、同値の並び、NULLの位置、ページ境界、重複。 |
| `state` | 初期データ、事前状態、合法・不正な遷移、差分更新、整合性、既存データの読み戻し。 |
| `failure` | 不正入力、境界外、部分失敗、タイムアウト、ロールバック、再試行、重複の防止。 |
| `concurrency` | 競合する更新、排他・分離レベル、同時到着、順序、並列時の不変条件。 |
| `performance` | 代表負荷とデータ量、上限、レイテンシー・処理量・資源の判定基準。 |
| `auth` | 許可と拒否、ロールの境界、所有権、拒否時に生じてはならない作用。 |
| `logs` | ログ・監査・メトリクス、識別情報の対応、欠落・重複、機微値を出さない契約。 |

調査軸の適用判定と比較項目の分母を、ケース案より先に決める。同じ状態でも許可と拒否で観測が異なるなら、別の比較項目にする。逆に、一つのアサーションを複数の行へ貼る場合は入力や期待が本当に同じかを点検する。 `high` の判定例は誤った金額、データ欠損、権限逸脱、外部送信の重複、復旧不能な失敗。対象の障害影響に照らして決める。

### 比較ルール

| `mode` | 必須フィールド | 判定 |
| --- | --- | --- |
| `exact` | `predicate` | 型・存在・値・件数・順序のうち、契約に含まれる特性を明示する。構造比較では未知項目の扱いを決める。 |
| `normalize` | `predicate`, `transform` | 対象を限定し、変換前提、両側の変換、許容幅と単位、変換不能時の失敗を決める。ソートが同順位や重複を消さないことを確認する。 |
| `exclude` | `reason`, `safeguard` | 除外する値を1項目に絞る。除外値が担っていた存在・形式・一意性・他項目との関係など、保持すべき性質を検証する比較項目IDを `safeguard` に置く。同じフィールドに値の除外と形式などの別の比較を登録できる。 |
| `intentional` | `decision`, `current_expected`, `candidate_expected`, `expected_values` | 既存の合意を示す仕様節・チケット・明示指示を `decision` に記す。`expected_values` に `old` と `new` の期待値をJSONの値で指定し、旧新それぞれの実測を照合する。 |

未知の差分は、一致扱いや意図的差分に変更せず調査する。正規化や除外を適用する前の観測も、機密を除いた再現用記録として保存する。例えばタイムスタンプの等価性をUTC換算で比較するなら、異なる瞬間は失敗させ、欠損や解釈不能な値も明示的に扱う。生成IDを比較から外す場合も、レスポンス・永続化・イベントで同じ論理対象を参照していることを観測する。

## ケースの実行条件

- 同じ論理データを独立したDB・ファイル・キュー等へ復元し、件数、キー、関連、値、設定をケース前に照合する。IDが物理的に異なるときは論理キーの対応を立てる。時計、タイムゾーン、乱数、locale、ジョブの完了条件を固定または記録する。ケース間はリセットし、順序が契約の一部ならケース内で操作順を表現する。
- ファイルやデータの書き込みはコミット後に読み戻し、追加・更新・削除、件数、内容、制約、ロールバックを比較する。外部送信は許可された隔離環境で送信先を確認し、実送信を遮断してローカル受信器や許可済みサンドボックスで観測する。外部呼び出しを置換する位置と代替の応答条件を記録し、業務ロジックや永続化の経路は実装を通す。非同期の無作用を確認するときは、処理完了やキュー排出までの上限を決める。
- 排他はバリア等で対象操作が実際に重なったことと、最終状態や成功件数を確認する。性能は現新で環境と負荷を揃え、ウォームアップ、試行回数、指標、許容閾値の根拠を計測前に記録する。比較環境や判定基準が整わなければ、測定記録と未検証理由を残す。
- 現行と新の差を報告する場合、同一入力・初期条件、ケースID、比較ルール、伏字を適用した現新の観測とコマンドを残す。テスト失敗、比較元や観測手段の不足、許可された差分、環境の不備は、それぞれの根拠を記す。

## 実行証拠JSON

テストランナーで `old.json` と `new.json` を別々に作る。各ファイルの形式は次のとおり。旧新で同じケース・採取点の ID を使い、観測した入口、引数、事前状態から `values` を記録する。

| キー | 採取する内容 |
| --- | --- |
| `side`・`revision`・`plan_sha256` | `old` または `new`、実際に実行したリビジョン、計画ゲートが出力したハッシュ。ハッシュは独立一覧・条件・計画を含む。旧の過去の採取を使うときは、元の記録とリビジョンを照合して対応する採取点に割り当てる。 |
| `steps` | 採取点の配列。各行にケースIDの `case`、採取点IDの `step`、通った `target`、実際の `values`、採取した `outputs` を記録する。同じケース内の採取順を保つ。 |
| `controls` | 許容・拒否や高リスク回帰の確認用の採取点。各行に両側で共通の `id` と `outputs` を記録する。通常の比較と別に採取する。 |

`outputs` は観測IDをキーにしたオブジェクトで、各値に `raw`（採取したJSON値）を入れる。正規化する観測には `normalized`（テストと同じ正規化処理を適用した値）も入れる。たとえば `{"O-exit-code":{"raw":2},"O-stderr":{"raw":"invalid_limit\n"}}`。`null` を採取した場合には `raw: null` を記録する。採取しなかった場合は観測IDを省き、未検証として扱う。比較除外の値は、対応する保護リスクを比較する採取点で採取できる。出力へ残せる値には必要に応じて伏字を適用し、比較すべき違いを潰さないことを確認する。

`results.json` は実行ファイルを指す索引として作る。用意する項目は次のとおり。

| キー | 形と条件 |
| --- | --- |
| `plan_sha256` | 計画ゲートが出力したハッシュ。 |
| `executions` | `old` と `new` を持つオブジェクト。各値は `{"path":"old.json","sha256":"…"}` の形とし、パスは `results.json` を置くディレクトリ内に置く。SHA-256 は保存したファイルのバイト列から求める。 |
| `rule_checks` | `normalize`、`exclude`、`intentional` の観測IDごとに `observation` と、異なる採取点の `accept`・`reject`（`controls` のID）を指定する。許容側で実際の差があり、比較が通り、拒否側で保持すべき差が検出される必要がある。除外では、許容側で除外値と保護対象の両方を、拒否側で保護対象を採取する。 |
| `negative_checks` | 高リスクごとに `risk` と `control`（`controls` のID）を指定する。採取した旧新の値を同じルールで判定して失敗することを確認する。対象がなければ空配列。 |
| `premortem` | 下表の全キーを持つオブジェクト。値は `{"status": "checked" または "open", "evidence": "照合した位置・結果または未解決の理由と次の検証"}`。 |

`verify` は両ファイルの存在、ハッシュ、リビジョン、採取順、入力・状態と採取出力を照合し、判定を再計算する。起動や初期化の失敗で値を採れなかった項目は未検証として残す。実行不能時は採取できた範囲と理由を報告する。正規化の意味と採取した値の由来は、実際のテストコード・操作・根拠で確認する。

終了コードは全項目の比較を確認できた場合に0、未実行・不一致・調査や比較ルールの未確認がある場合に1、必要なファイルなし・不正な形式・ハッシュ不一致などの場合に2。比較項目ごとの比率は項目数を分母とする。旧書式の計画は構造だけを表示できる。完了判定には、独立一覧、採取点を持つ計画、両側の実行ファイルが必要。

## プリモーテム

「全ケースが成功した直後に現新差分が見つかった」と仮定し、表の反例を実際のソース、テスト、観測記録と照合する。確認した根拠を `premortem` に記し、発見した未解決事項は `open` にする。

| キー | 確認する反例 |
| --- | --- |
| `inventory` | 新旧の片方だけにある入口、旧データ専用の分岐、失敗時にしか動かない書き込み先が台帳から落ちている。最初の列挙元とは別の入口または依存の一覧から逆に辿る。 |
| `oracle` | 比較元が別リビジョン・別の初期条件・新の出力・仕様の推定だった。代表ケースと各高リスク項目の来歴と取得手順を照合する。 |
| `assertions` | ケースが成功しても、副作用や拒否時の無作用を判定するアサーションが実行されていない。コードとランナー出力を突き合わせ、高リスクの反例が対象のアサーションを落とすことを確認する。 |
| `state` | ケース間のデータが使い回され、単独・順序変更で判定が変わる。非同期の観測が早すぎるか、送信先の遮断が設定値の確認だけで終わっている。初期状態照合と終了時の証拠を見る。 |
| `rules` | 一括マスク、無条件ソート、過大な許容差で差分が消える。意図的差分を合意済みと取り違える。比較前のデータ、許容・拒否の確認、合意の出典を照合する。 |

設計技法の参照先。差分比較と誤検知は [McKeeman, Differential Testing for Software, pp. 100–107](https://www.mrynet.com/FTP/os/DEC/dtj_v10-01_1998.pdf)。根拠とケースの対応及びケース設計は [ISTQB CTFL v4.0.1, §1.4.4・§4.2](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)。状態依存は [pytest, Flaky tests](https://docs.pytest.org/en/stable/explanation/flaky.html)。回帰を意図的に入れる確認は [Practical Mutation Testing at Scale](https://arxiv.org/abs/2102.11378) を参照した。
