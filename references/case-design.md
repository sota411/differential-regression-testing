# 比較する境界ごとの現新テスト設計

## 比べる出力と旧新の対応

同じ機能でも、入口への到達、処理結果、画面の表示で出力と調べる場所が変わる。依頼の範囲に該当する境界を選び、旧と新の対象を、利用側から見て同じ意味を持つ条件で対応付ける。

| 境界 | 何を見て項目を見つけるか | 何を旧新で比較するか |
| --- | --- | --- |
| 入口・経路 `routing` | ルート登録、URL・メソッド・クエリ・ヘッダーによる振り分け、プロファイル、利用側の呼び出し。旧新それぞれの一覧を照合し、経路ごとの到達・拒否・リダイレクトを候補にする。 | 応答ステータス、論理的な到達先、リダイレクト先。コントローラー名が移行で変わる場合は、同じ業務操作を指す対応を記録する。 |
| 処理結果 `service` | 呼び出し元、既存の業務シナリオ、判定の順序、入力検証、例外処理、設定で付く処理。成功・拒否・途中失敗の振る舞いに結び付く条件を拾う。 | 実際の戻り値・応答のフィールド、エラーの構造、契約に含まれる永続化と外部作用。 |
| SQL・永続化 `sql` | SQLやクエリビルダー、動的条件、バインド値、結果マッピング、トランザクション。絞り込みの有無、境界、該当なし、結合で重複する行、更新対象の有無を根拠から選ぶ。 | 取得した値・型・件数・重複・契約上の順序、更新件数やコミット後の状態。SQL文字列は動作を調査する手掛かりに使い、利用側が依存する結果を採る。 |
| 画面 `view` | テンプレートの表示条件、イベント定義、文言や操作の仕様、実際の操作順。該当なし、権限による表示差、選択・操作可否が切り替わる状態を作る。 | 対象要素の表示値・文言・選択状態・操作可否・画面遷移。利用者の操作を比較する場合は実ブラウザで再現し、必要に応じて見た目も採取する。 |
| ジョブ・ファイル・メッセージ `job` | スケジュール・購読登録、入出力の定義、チェックポイント、再実行条件、後続処理の契約。空入力、部分失敗、再開など該当する条件を拾う。 | 終了状態、生成物の有無・件数・内容、再実行後のデータ、生成されたイベントの件数・順序・内容。 |

この表は対象に合う調査の起点として使う。CLIなど別の境界には `other` を使い、同じ要領で入力元と出力を定める。入口登録、動的SQL、実ブラウザによる採取の例を参照できる。[Spring Bootのルート情報](https://docs.spring.io/spring-boot/api/rest/actuator/mappings.html)・[MyBatisの動的SQL](https://mybatis.org/mybatis-3/dynamic-sql.html)・[Playwrightのトレース](https://playwright.dev/docs/trace-viewer)

## 振る舞いの根拠を探す順序

1. **選んだ出力から調べる場所を決める。** 上表の定義や実効設定から、分岐、書き込み、例外処理、外部送信までたどる。コンテナ設定やラッパーが加える処理は、登録元・適用条件・適用順をたどる。業務メソッドの外で動く送信・監査・例外処理も観測の対象に含める。
2. **異なる起点から逆に照合する。** 変更された分岐・設定キー・SQL・送信先と、現行の利用側・ジョブ定義・既存テスト・利用記録から該当する境界へ戻る。無変更ファイルの旧分岐、途中失敗時だけ動く経路、現新片方だけの登録を探す。適用なし・未確認には根拠や残る調査を記録する。
3. **現行の振る舞いを確かめる。** 小さく再現するか、条件が一致する採取済み記録を使う。設定で変わる既定値や暗黙の利用条件も拾う。実測前の期待値は推定とし、仕様と実測が食い違うときは双方を残す。根拠は `revision:path:line`、仕様節、記録IDなどで示す。

## 根拠から条件を列挙する

- **具体的な対象を列挙できるときは `rows`。** 登録済みの「メソッド＋URL」、画面の個別な表示分岐、互いに独立しない条件など、確認できた組を1行ずつ置く。既存設定にある `GET /items` と `POST /items/filter` なら、この2行を登録する。
- **組み合わせで出力が変わるときは `axes`。** 入力・状態を等価分割し、意味のある軸を組み合わせる。順序のある閾値は直前・一致・直後、型の違いは欠損・NULL・空・ゼロを根拠に従って分ける。たとえば検索語の有無と、データが0件・複数件である状態を組み合わせる。
- **失敗や再送でも出力を決める。** 何が起きるかに加えて、起きてはいけない書き込み・送信を条件ごとに採る。状態・操作の順序が重要なら実際の操作列を作る。性能、排他、文字コード、TZなどは、比較する出力に差を生む具体値・設定があるときに条件へ加える。

到達可能な条件の組を定義する。不正な操作を試せる場合は拒否を比較する候補に含める。相互作用しない項目は別のモデルに分ける。組み合わせを減らす場合は採用した方式、必須の組、調べない組を記録する。[ISTQB CTFL v4.0.1 §4.2](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)・[NIST SP 800-142](https://csrc.nist.gov/pubs/sp/800/142/final)

## 独立した必須項目を条件と計画に対応付ける

仕様、旧の出力契約、レジストリ、利用側などから比較が必要な項目を抜き出し、ケースと条件表を作る前に `inventory.json` を作る。別の資料や起点から逆引きして、各対象の条件と出力が落ちていないか確認する。項目を減らすときは、到達不能、移行対象外、契約変更などの根拠を残す。`inventory.json` には `requirements` 配列を置き、各要素に `target`、`boundary`、`values`、`layer`、`field`、`evidence` を記す。機械的に取り出せるルートや公開スキーマは、手書きのケース表を経由せず列挙する。[CLIの独立した必須項目の例](../assets/inventory-example.json)

その一覧を基に `conditions.json` を作る。[商品検索の境界別例](../assets/search-conditions-example.json) と、[CLIの条件例](../assets/conditions-example.json)を参照する。

| キー | 内容 |
| --- | --- |
| `models[].id`、`target`、`boundary` | 一意のモデルID、`plan.json` の入口ID、最初の表で選んだ境界。 |
| `evidence` | 対象と旧新の対応、代表値や出力を選んだ根拠。 |
| `rows` または `axes` | どちらか一方。 `rows` は `values`（条件名から文字列の値への対応）と `evidence` を持つ行の配列。 `axes` は条件名から代表値の文字列配列への対応。空文字を入力する場合は、長さ0を示す明示的なラベルを使う。 |
| `outputs` | `direct`、`state`、`effects` のうち必要な層ごとに、実際に比較する個別項目名を配列で指定する。 `plan.json` の `observations[].field` と同じ名称を使う。たとえば終了コードと標準エラーは別項目にする。 |

`design` は `rows` をそのまま列挙し、`axes` を組み合わせに展開する。 `plan` は独立一覧と条件表の条件・出力が一致し、各項目が計画にあることを検査する。条件表から新たな確認事項が出たら、先に根拠とともに独立一覧へ追加する。 `risks[].design` に `model`、展開結果と同じキー・値の `values`、実際に失敗させたい具体的な `regression` を記入する。旧や観測が利用できない項目は、候補に残して `gap` を付ける。比較を実装できる項目については、`cases[].steps` の採取点ごとに同じ `target` と `values` を書き、どの比較項目を担当するかを `covers` で指定する。

コード生成前に、①操作でその条件に到達する、②対象の出力と比較方法で回帰を検出できる、③根拠を逆にたどって未登録の条件や出力が残っていない、の3点を照合する。複数操作の `scenario` は手順を番号で区切り、各比較項目の採取時点を書く。たとえば「1. 注文を登録し、両側の登録済み状態を確認。2. 同じキーで再送。応答と新規通知件数は手順2の直後に採る」。

ケースを書いた後で条件を変更する場合は、追加で見つけた根拠、到達不能、または他の値と同じ振る舞いになる根拠を残してから `design` を再実行する。
